# Marketplace slice D: fulfilment and messaging

**What shipped:** after an expert accepts, the two sides can work the booking to the end. Conversations (before a booking and on one), private file sharing (briefs, messages, deliveries), delivery and acceptance with revision rounds, auto-release timers, "attach from Documents", a Calendar meeting and `.ics` for consultations, founder in-app notifications, expert emails, and the three slice C lows. API only. **No money moves in this slice**: accepting a delivery records the decision and publishes `marketplace.delivery.accepted` for slice E to hook. Branch `feature/marketplace-fulfilment`, PR: see the branch (not merged). Migration **`0104_marketplace_fulfilment`**, `down_revision = 0105_analytics_custom_metrics` (the develop head at the time). FE guide `docs/fe-integration-guide-marketplace-fulfilment.md` (live-captured, `e2e/test_marketplace_fulfilment.py`).

**Why:** slice C stops at `confirmed` / `in_progress`. Founders need to brief the expert, talk to them, receive the work, ask for changes and close the booking; experts need an inbox for all of that; and the platform needs deadlines so a delivery nobody answers does not hang forever. Gap rows 18, 20, 24-29, 57, 58 of `cofoundaz/docs/checklist/marketplace-prd-gaps.md`; design `cofoundaz/docs/superpowers/specs/2026-11-05-marketplace-design.md` §3.4, §3.7, §5-§7, §9; decisions D-MP-L1 (only founders write), L10 (brief files, Documents), L11 (staff read threads only inside a dispute).

**How**

| Topic | Decision |
|---|---|
| Tables | `marketplace_deliveries` (one row per hand-over, with the founder's decision), `marketplace_threads` (one open pre-booking thread per workspace and expert by a partial unique index; one thread per booking), `marketplace_messages` (plain text, 1 to 4000 characters by CHECK, a read stamp per side), `marketplace_booking_documents`. Columns: `marketplace_files.thread_id`, `marketplace_bookings.overdue_notified_at`, `marketplace_orders.attention_resolved_at/by`. Partial indexes for the two timers (`auto_release_at` where delivered; `due_at` where in progress and not yet notified). |
| Locks | Slice C's order: booking row first, then order, then expert only when needed. Deliveries and messages never take an order lock. Posting locks the thread row only (serialises the email digest stamp) and reads the booking unlocked, so it cannot deadlock with `apply_payment` (booking, order, expert, thread). Every transition re-reads its status under the lock; replays are no-ops. |
| "Was paid" | One predicate (`identity.was_paid` / `paid_clause`): a booking reached `awaiting_provider` or later; a closed one counts only if its order took money and it did not close as `payment_not_completed`, `payment_review`, `slot_no_longer_available` or `booking_closed`. Experts see only paid bookings (reads, files, threads, documents); a thread is only ever attached to a paid booking. Found in review: without it a lapsed checkout could take the pair's live pre-booking thread. |
| Deliveries | Package: `in_progress` to `delivered` (`auto_release_at` +7 days) to `completed`, or back to `in_progress` on a change request while `revisions_used < revisions_included_snap`. Consultation: `complete` after the session ends, or the timer, gives `delivered` with `auto_release_at` = the later of the session end and now, plus 48 hours (so a late worker still gives the founder two days, and one tick never delivers and releases the same booking). The decision is recorded on the delivery row (`accepted`, `changes_requested`, `auto_released`). Accepting a booking already completed (by you or by the timer) is a 200 replay. |
| Money | Untouched. Accept and auto-release both publish `marketplace.delivery.accepted` (auto-release adds `auto_released: true` and a separate `marketplace.delivery.auto_released` for the founder notice). **Slice E subscribes to `accepted` only.** |
| Timers | `timers.tick` gained three steps, each `SKIP LOCKED`, one booking per transaction, emails flushed after commit, a failing booking logged and skipped: deliver ended sessions, auto-release, flag overdue packages once (notice only). The tick's result dict gained `consultations_delivered`, `auto_released`, `overdue_flagged`. |
| Files | Purposes `brief`, `message` (founder: PDF, Word, Excel, PNG, JPEG, 10 MB) and `delivery` (PDF, Office, images, text, CSV, 15 MB), magic-byte checked by the Documents sniffer. Unsent files are the uploader's alone. Attaching locks the rows in id order and fails with one uniform `INVALID_FILE` (never reveals someone else's file). Readable once attached by founder-side members of that workspace and by that booking's approved expert; booking briefs are checked before anything is created. Experts upload through the existing `/provider/files` (they have no workspace). A file already sent cannot be deleted. |
| Threads | Founder side reads (founder + team member), only a founder posts and opens (D-MP-L1). An expert replies but cannot open a conversation, and an empty one is invisible to them. Reads mark the other side's messages read for the whole side. Reading never creates or locks a thread; only a founder's POST (or payment) does. Closed (cancelled, declined, expired, refunded) bookings are read-only. Limits: 30 posts a minute, 20 opens a minute, 20 new conversations per workspace per day. Expert emails: one per conversation per 10 minutes, no message text. |
| Documents | **Not** `document_grants`. Those never expire, would list the document in the expert's Shared-with-me page and name the workspace to them. `marketplace_booking_documents` links one booking to one document of the workspace, 30 days, revocable, revoked on every ending, and the expert reads it through the booking only. Alternative rejected: extending `document_grants` with an expiry (it changes a security surface shared with Documents, and still exposes the workspace name). |
| Calendar | On accept of a consultation: `meetings.create_meeting` (team-visible, the expert as external attendee, no AI note-taker, no brief in the description), `source_ref = marketplace:<id>`; the existing `calendar.invites` job sends the invite with the `.ics`. Closing a booking (`closing.on_closed`, called by cancel, decline, expiry) deletes the event and sends the cancel. A Calendar failure is logged and never undoes the accept. `GET .../calendar.ics` is addressed to whoever downloads it. |
| Notifications | New `marketplace` preferences row (in-app on, email off). Founder in-app kinds (founders only): confirmed, declined, expired, overdue, delivery submitted, delivery auto-released, new message (once per conversation per 10 minutes; **title only, never the text**, because a notification can be emailed). Payloads carry names and ids, never the brief. |
| Slice C lows | (a) `unverified_close` clears itself when the order is later paid-and-revived or fully refunded (`attention_resolved_at`; the flag stays as the record); staff can resolve any flag with `POST /admin/marketplace/orders/{id}/attention/resolve` (reason 10+ characters, audited with IP and user agent, **authenticator code required for money flags**; new problems re-open it); the queue hides resolved ones (`?resolved=true` lists them). (b) `flag_attention`'s log line no longer says "Paystack reports None". (c) Replay test: a late mismatching payment on a closed hold emails the founder once. |

**Operate / roll back:** no new settings. The worker must have the notifications registry registered (it does at start-up) for founder notices. Roll back with `alembic downgrade 0101_marketplace_booking`: it **drops** `marketplace_deliveries`, `marketplace_threads`, `marketplace_messages`, `marketplace_booking_documents` and the added columns and indexes, deleting every conversation, delivery record and shared-document link. Files already uploaded stay in storage (their rows keep working, minus `thread_id`). Do not roll back once experts have delivered.
