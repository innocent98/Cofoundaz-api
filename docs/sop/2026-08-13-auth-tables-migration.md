# SOP: Alembic migration for auth tables

## What shipped

- Commit: `0f0da72` — `feat(db): migration for auth tables`
- Branch: `feat/auth-endpoints`
- Task 2 of the Auth Endpoints plan
  (`.superpowers/sdd/2026-08-13-auth-endpoints/task-2-brief.md`).

Autogenerated `alembic/versions/0002_auth_tables.py`, materializing the four
auth tables (`auth_sessions`, `auth_tokens`, `mfa_backup_codes`,
`oauth_accounts`) that Task 1 added to `Base.metadata`
(`app/db/models/auth.py`, commit `4b5cb23`). `alembic upgrade head` now takes
a `cofoundaz-api_db` at `0001_initial_schema` to `0002_auth_tables` cleanly.

## Why

Task 1 defined the four ORM models but they weren't reachable by any
migration — `alembic upgrade head` from `0001_initial_schema` would leave the
DB without them, so nothing built on top (session/token services, etc.) could
run against a real database. This task closes that gap.

## How

- Ran `poetry run alembic revision --autogenerate -m "auth tables" --rev-id
  0002_auth_tables` against the dev DB (already at `0001_initial_schema`).
  Autogenerate log showed exactly 4 added tables and 5 added indexes (the 4
  standard `user_id` FK indexes plus one extra on `auth_sessions.family_id`,
  which the model declares `index=True`) — no other tables touched, nothing
  spurious to remove.
- Renamed the generated file from Alembic's default
  `0002_auth_tables_auth_tables.py` to `0002_auth_tables.py` per the brief —
  cosmetic only, `revision`/`down_revision` inside were already correct
  (`down_revision = '0001_initial_schema'`).
- Hand-reviewed `upgrade()`/`downgrade()`: all constraint/index names are
  explicit via `op.f(...)`, driven by the project's `NAMING_CONVENTION`
  (`app/db/base.py`), consistent with `0001_initial_schema.py`'s style. Left
  the body untouched — no spurious ops, no manual edits needed.
- Enum columns (`auth_tokens.purpose`, `oauth_accounts.provider`) use
  `native_enum=False` (VARCHAR, no Postgres enum type), matching how every
  other enum in this project is handled — no new Postgres types introduced.
- Verified the downgrade is real, not just compile-passing: ran
  `alembic downgrade -1` → `alembic current` (back to `0001_initial_schema`)
  → `alembic upgrade head` (forward again to `0002_auth_tables`) on the dev
  DB. Clean round-trip. Since these are brand-new, never-deployed tables, the
  downgrade is fully lossless.

## What's involved

- `alembic/versions/0002_auth_tables.py` (new) — creates `auth_sessions`,
  `auth_tokens`, `mfa_backup_codes`, `oauth_accounts`, each with:
  - PK on `id`, FK `user_id` → `users.id` ON DELETE CASCADE (indexed).
  - `auth_sessions`: UNIQUE `refresh_token_hash`; extra index on `family_id`.
  - `auth_tokens`: UNIQUE `token_hash`.
  - `oauth_accounts`: UNIQUE `(provider, provider_account_id)`
    (`uq_oauth_accounts_provider_provider_account_id`).
  - `mfa_backup_codes`: no additional unique constraint beyond PK/FK.
- `tests/test_auth_migration.py` (new) — shells out to
  `alembic upgrade head` then inspects the DB via `sqlalchemy.inspect` to
  confirm all 4 table names are present.
- Database: `postgresql://user:password@localhost:5433/cofoundaz-api_db` (the
  compose dev DB) — now has all 11 tables (7 from `0001` + 4 new), pinned at
  `alembic_version.version_num = 0002_auth_tables`.

## Operate / roll back

- To apply: `poetry run alembic upgrade head` (from `0001_initial_schema` or
  any earlier state) — requires a reachable `DATABASE_URL`.
- To roll back: `poetry run alembic downgrade -1` drops all four tables and
  their indexes/constraints, restoring exactly the `0001_initial_schema`
  shape (round-trip verified above). Safe/lossless since nothing has been
  deployed against these tables yet; once real session/token data exists in
  production, treat this downgrade as destructive and confirm before running.
- Lock duration on prod-sized data: negligible regardless of `users` table
  size — `CREATE TABLE` takes an `AccessExclusiveLock` but on brand-new empty
  relations with no existing traffic, there's nothing to block.

## Follow-ups

- None required for schema correctness (no-drift check confirmed clean).
- `auth_tokens.token_hash` and `auth_sessions.refresh_token_hash` are unique
  globally (not scoped per-user), per the Task 1 model definitions — worth
  keeping in mind if token-generation format ever changes, since a collision
  anywhere in the table (not just per-user) raises `IntegrityError`. Not a
  migration-layer concern; flagged for the backend engineer's awareness when
  building the session/token services on top of these tables.
- Next task in the plan will build the service/endpoint layer against these
  tables (`auth_sessions` for refresh-token rotation, `auth_tokens` for
  email-verification/password-reset, `mfa_backup_codes`, `oauth_accounts`).
