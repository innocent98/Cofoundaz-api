# SOP — Module 19 Calendar (events CRUD, one range-filtered list for three views, read-only roadmap-milestones projection)

**What shipped** — Module 19 in full (PRD 19). **Module 19 is complete**; its heavy pieces were
deferred by agreement, not left half-built.

1. **`calendar_events` store** — a per-workspace table of things on a calendar
   `(title, type, event_date, start_time?, end_time?, all_day, description?, created_by?)`; new
   `CalendarEventType` enum (`milestone`/`meeting`/`deadline`/`task`), stored by value.
2. **Events CRUD** — `POST/GET/PATCH/DELETE /calendar/events`, with the PATCH time rules checked
   against the **merged** row rather than the payload alone.
3. **One list, three views** — `GET /calendar/events?date_from=&date_to=&type=`. Month, Week and
   Agenda differ only in the range they request; grouping and formatting stay on the front end.
4. **Read-only milestones projection** — `GET /calendar/milestones` reads **Roadmap's** existing
   `RoadmapMilestone` rows through a three-table join and derives the four badges the UI shows
   (`complete`/`at_risk`/`on_track`/`not_started`). **No milestone table was created**; editing a
   milestone stays in Roadmap.

(`service.py`, `milestones.py`, `errors.py`), 6 new routes under `/calendar` behind

## Why

The PRD's Calendar is the "where does my time go, and what's due" layer. The FE prototype
(`app/(dashboard)/calendar/`) has five screens: Month, Week, Agenda, Milestones and Sync.

The scoping decision that shaped the whole module: **milestones already exist.**
`RoadmapMilestone` has lived in Roadmap since Module 05, so the Milestones tab reads it rather
than duplicating it. That was the lead's explicit instruction and the main design trap in the
module.

The second decision was about time. **There is no timezone field anywhere in this codebase** —
`Startup` carries `country` and nothing else. Converting between timezones without knowing
anyone's timezone is how a 2pm meeting renders as 1pm, so v1 does not convert at all.

## How

**Access (spec D4).** Founders and team members only, for reads and writes alike. Accountant is
**not** granted — unlike Finance, where it is. A calendar is not finance-scoped, and widening a
role set later is cheap where narrowing one after the FE ships is not.

**Tenancy.** `startup_id` comes from the `Membership` the role dependency returns, never from the
body or query. Every events query filters on it; a cross-workspace id raises `NotFound` → a
uniform **404**, never 403, so one workspace cannot detect another's row ids.

The milestones projection is the exception worth understanding: `RoadmapMilestone` has **no
`startup_id`**. It scopes through `phase_id → RoadmapPhase.roadmap_id → Roadmap.startup_id`, so
the three-table join **is** the tenancy boundary — there is no column to fall back on if the join
is wrong. `tests/services/calendar/test_milestones.py` builds two full roadmap chains under two
workspaces specifically to prove it holds.

**Dates and times (spec D6).** `event_date` is a plain `Date`; `start_time` and `end_time` are
naive `Time`. Everything is local wall-clock, stored exactly as sent and returned as
`YYYY-MM-DD` and `HH:MM`. Nothing converts. "Today", where it is needed, is
`datetime.now(UTC).date()`, matching Finance's `cashflow.py`/`runway.py`.

The `HH:MM` promise is kept by a `field_serializer` on `EventResponse` rather than at each call
site — `model_dump(mode="json")` would otherwise emit `HH:MM:SS`, and a convention applied by
hand at five call sites is one someone eventually forgets.

**`all_day` is declared, never inferred (spec D12).** An event with no times is *untimed*, which
is not the same as all-day: "VAT filing due" has no clock time but should not block out a day.
The front end sends the flag explicitly; the column defaults to `false`. Sending `all_day: true`
*with* a time is a **422** rather than a silent discard (D9) — dropping data the caller sent is
worse than refusing it.

**PATCH validates the merged row.** `_check_times` is shared between create and update, and
update calls it against the merged values. Validating the payload alone would let
`{"start_time": "11:00"}` through against a row whose stored `end_time` is `"10:00"`, leaving the
row in a state a create would have refused.

**Ordering.** `event_date` ascending, then `start_time` ascending **NULLS FIRST**, then
`created_at`. The `nullsfirst()` is deliberate: Postgres defaults `ASC` to NULLS LAST, which would
push untimed and all-day events to the bottom of their day instead of the top, the opposite of
what the Agenda renders.

**Two deliberate divergences from the scheduler.** The projection mirrors
`_due_overdue_milestones` (`app/worker/scheduler.py:85`) but drops two of its filters:

- its `Startup.deleted_at.is_(None)` join — that function scans *every* workspace, while a
  request-scoped read already holds an active `Membership`. `resolve_workspace`
  (`app/db/tenancy.py:16`) applies no such filter either, so adding one here would be
  inconsistent with the rest of the app;
- its `_local(now)` clock, which resolves through `settings.SCHEDULER_TIMEZONE`. The two agree
  while that setting is `"UTC"` (its default), but the calendar's notion of "today" should not
  move when a scheduler config value changes.

Both are written into the docstring so nobody later reads "mirror the scheduler" and reinstates
them.

prefix, so the standalone index is strictly redundant; it is kept for consistency with the house
rule, which the lead accepted as a legitimate call.

## Operate / roll back

- No new environment variables, secrets or configuration. No new dependencies.
- **Roll back** with `alembic downgrade 0045_finance_model`, which drops `calendar_events` and its
  three indexes. **Lossy** — every calendar event in every workspace is destroyed. Roll the code
  back together with the migration: with the table gone, the five event routes fail.
  `GET /calendar/milestones` would keep working, since it owns no table, but it is served from the
  same router.
- **Rolling back destroys no Roadmap data.** The milestones projection only reads; nothing in this
  module writes to `roadmap_milestones`, `roadmap_phases` or `roadmaps`.
- **Access:** founders and team members. Accountant is deliberately excluded — if someone asks for
  it, add `MembershipRole.accountant` to `_calendar` in `app/api/v1/endpoints/calendar.py` and
  remove it from `FORBIDDEN_ROLES` in `tests/api/test_calendar.py`.
- **The Sync screen has nothing to call.** No calendar-connection endpoints exist. If a user
  reports the Sync tab doing nothing, that is v1 behaviour, not a fault.
- **Times carry no timezone.** Two users in different countries entering "2pm" produce the same
  stored `"14:00"` for different real moments. This is intentional and documented in the FE guide;
  it becomes resolvable only once a workspace timezone field exists.

## Follow-ups

- **Multi-day events.** A single `event_date` with no `end_date` means an all-day event cannot
  span days. Nothing in the prototype shows one, so v1 does not model it — recorded explicitly
  because it is the kind of limitation a front end assumes away. (Raised in spec review.)
- **External calendar sync** (Google / Outlook / Apple) — OAuth plus third-party APIs with no
  infrastructure in the repo. Same line drawn on Finance's integrations slice.
- **Cross-module aggregation into the Agenda** — the mock's "From your mission", "Roadmap
  milestone" and "Sales pipeline" rows. A large integration across missions, roadmap, finance and
  sales; v1 serves the calendar's own store, with the milestones read as the only reach outside it.
- **Reminder scheduler** ("remind me 3 days / 1 day before deadlines"). Scheduler infrastructure
  exists (`app/db/models/scheduled_run.py`, the roadmap-overdue tick) but v1 defers it, as Finance
  deferred invoice reminders. No domain events are published yet either — nothing would consume
  `calendar.event.created` until this lands.
- **Sync preferences** (block focus time, remind before deadlines, show weekends) — three toggles
  on a screen with nothing else to call. Not core.
- **Recurring events** — no recurrence UI anywhere in the prototype.
- **Unioning the two senses of "milestone"** into one Milestones list (the Roadmap projection plus
  milestone-typed calendar events). v2 enhancement; v1 keeps the two stores visibly separate and
  says so in the FE guide.
- **Pagination or a span cap on the events list.** Consistent with the shipped Finance transaction
  list, which has neither. Revisit if a workspace's calendar grows large.
- **`tasksInfo`, `AgendaItemData.subtitle`, and the "N of M complete this quarter" header** have no
  backend source. Omitted rather than faked, and labelled not-backed in the FE guide. The quarter
  count is cheaply derivable from the projection if anyone asks for it.
- **Regenerating the FE guide from real captures** after the first live e2e run, and deleting its
  provenance note. Its values are currently illustrative.
- **Regenerating the FE repo's `openapi.json`** (a staging snapshot with no calendar paths). Not
  this module's work; the lead is tracking it.
