# SOP: Initial Alembic migration (foundation schema)

## What shipped

- Commit: `7af08b1` — `feat(db): initial Alembic migration for foundation schema`
  (fix round 1: `tests/test_migrations.py` strengthened — see below)
- Branch: `design/auth-onboarding-foundation`
- Task 13 of the Foundation & Tenancy Spine plan
  (`.superpowers/sdd/2026-08-12-foundation-tenancy-spine/task-13-brief.md`).

Pointed Alembic at the ORM models and autogenerated the first real migration,
`0001_initial_schema`, which materializes all 7 tables that Tasks 10–12 added to
`Base.metadata` (`users`, `user_profiles`, `startups`, `startup_profiles`,
`memberships`, `jobs`, `audit_log`). `alembic upgrade head` now runs clean against
an empty Postgres database.

## Why

Tasks 10–12 defined ORM models but relied on `Base.metadata.create_all()` in the
test harness — there was no way to stand up a real (dev/staging/prod) database.
`alembic/env.py` still had a stub `# Import all models here` comment and no models
registered on `target_metadata`, so `alembic revision --autogenerate` would have
produced an empty migration. This task closes that gap so the schema is
deployable via the normal Alembic upgrade path.

## How

- **`alembic/env.py`**: replaced the commented-out model-import stub with
  `import app.db.models  # noqa: F401` (registers every table via the package's
  `__init__.py`) so `target_metadata = Base.metadata` (already present) actually
  sees the tenancy/jobs/audit tables. Reformatted via `black`/`isort` (alembic is
  excluded from repo-wide lint config, but this file was checked/formatted
  explicitly since it's a task deliverable).
- **`alembic/versions/0001_initial_schema.py`** (new, autogenerated then
  hand-edited): ran
  `poetry run alembic revision --autogenerate -m "initial schema" --rev-id 0001_initial_schema`
  against the empty dev DB, then:
  - Renamed the output file from Alembic's default
    `0001_initial_schema_initial_schema.py` to `0001_initial_schema.py` to match
    the brief's required filename.
  - Added `op.execute("CREATE EXTENSION IF NOT EXISTS citext")` as the first
    statement in `upgrade()`, before any `op.create_table(...)` call — required
    because `users.email` uses the `CITEXT` Postgres extension type and the
    extension must exist before the column can be created.
  - Left the rest of the autogenerated body as-is: it already imports
    `from sqlalchemy.dialects import postgresql` and references
    `postgresql.CITEXT()` (for `users.email`) and `postgresql.ARRAY(sa.String())`
    (for `startup_profiles.goals`) correctly — Alembic's default codegen uses the
    module-qualified form rather than named imports, which is equivalent and
    standard.
- No model changes. Autogenerate produced exactly the 7 tables with no
  unexpected diffs, so there was nothing to reconcile against Task 10–12 models.

## What's involved

- `alembic/env.py:1-14` — model import / `target_metadata` wiring.
- `alembic/versions/0001_initial_schema.py` (new) — the migration itself: creates
  the `citext` extension, then `audit_log`, `jobs`, `users`, `startups`,
  `user_profiles`, `memberships`, `startup_profiles` (in dependency order — FK
  parents before children), plus the indexes defined on the models
  (`ix_audit_log_actor_created`, `ix_audit_log_startup_created`,
  `ix_memberships_startup_id`) and unique constraints
  (`uq_users_email`, `uq_memberships_user_id_startup_id`).
- `tests/test_migrations.py` (new) — `test_alembic_upgrade_head_runs`: shells out
  to `poetry run alembic upgrade head` and asserts `returncode == 0`.
- Database: `postgresql://user:password@localhost:5433/cofoundaz-api_db` (the
  compose dev DB) — now has all 7 tables plus `alembic_version` (pinned at
  `0001_initial_schema`).

## Operate / roll back

- To apply on a fresh environment: `poetry run alembic upgrade head` (requires
  `DATABASE_URL` pointing at a reachable Postgres instance; the migration
  self-creates the `citext` extension, no manual DB prep needed beyond a
  connectable superuser/owner role that can `CREATE EXTENSION`).
- To roll back: `poetry run alembic downgrade -1` drops all 7 tables (does **not**
  drop the `citext` extension — extensions are left in place by design, since
  other migrations/objects may depend on it and `DROP EXTENSION` isn't safe to
  automate in a downgrade).
- This closes out the "no migration yet" caveat noted in the Task 10–12 SOPs
  (`2026-08-12-jobs-table-dispatcher-endpoint.md`,
  `2026-08-12-audit-log-write-audit-helper.md`,
  `2026-08-12-tenancy-spine-models.md`) — updated those docs' Operate/rollback
  notes to point here instead of "Task 13 will add this."

## Follow-ups

- None required for schema correctness (no-drift check confirmed clean). Future
  schema changes should go through the normal
  `alembic revision --autogenerate` → review → `alembic upgrade head` flow from
  here on.
- `alembic downgrade -1` intentionally leaves the `citext` extension installed;
  if a future migration needs to remove it, do so explicitly and only after
  confirming no remaining `CITEXT` columns reference it.
