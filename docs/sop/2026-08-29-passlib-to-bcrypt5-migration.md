# SOP — Migrate off passlib to direct bcrypt, unblocking bcrypt 5.0.0

> **Type:** dependencies / auth security · **Date:** 2026-08-29 · **Area:** `app/core/security.py`, `app/services/auth/password.py`, `app/core/errors.py`, `pyproject.toml`

## What shipped

Branch `chore/bcrypt-5-passlib-migration` (unblocks Dependabot PR #23):

| What |
|---|
| `app/core/security.py` — password hashing calls `bcrypt` directly; passlib removed |
| `pyproject.toml` / `poetry.lock` — `bcrypt ^4.0.1` → `^5.0.0`; `passlib` dependency **removed** |
| `app/core/errors.py` — new `PasswordTooLong` (`PASSWORD_TOO_LONG`, 422) |
| `app/services/auth/password.py` — `validate_password_strength` gains a 72-**byte** upper bound |
| `tests/fixtures/passlib_golden_hashes.json` — 126 hashes generated by the real pre-migration passlib |
| `scripts/gen_passlib_golden_hashes.py` — provenance for that fixture |
| `tests/core/test_password_hashing.py`, `tests/api/auth/test_legacy_passlib_login.py` — 303 new tests |

The dependency bump and the migration are **one commit each on one branch, deliberately not
separable**. Landing bcrypt 5 without the migration is a total auth outage; landing the
migration without bcrypt 5 leaves the reason for it undocumented in the diff.

## Why

### passlib cannot be fixed, only replaced

PR #23 fails every `tests/api/auth/test_login.py` test. The failure is **not** what the
traceback's `set_backend` frames suggest at a glance:

```
ValueError: password cannot be longer than 72 bytes, truncate manually if necessary
```

…raised while hashing a **9-character** password. The error comes from passlib's own one-time
bcrypt backend self-test, not from the user's password. `passlib/handlers/bcrypt.py`
`detect_wrap_bug()` probes for the BSD `$2a$` wraparound bug by hashing a hardcoded 255-byte
secret:

```python
secret = (b"0123456789"*26)[:255]
```

bcrypt 5.0.0 raises `ValueError` above 72 bytes where bcrypt 4 silently truncated
([pyca/bcrypt#1078](https://github.com/pyca/bcrypt/commit/5060bce)). So the backend never
finishes loading, and **every** call fails through `_stub_requires_backend` → `set_backend`
regardless of password length. Reproduced directly:

```python
CryptContext(schemes=["bcrypt"]).hash("short")   # 5 bytes
# ValueError: password cannot be longer than 72 bytes
```

There is no configuration that avoids this and no upstream fix coming. **passlib's latest
release is 1.7.4, published 2020-10-08** (verified against the PyPI JSON API — no 1.7.5, no
2.x). The only alternative was pinning `bcrypt<5` permanently, which forfeits every future
bcrypt security fix.

A second, quieter symptom was already present at bcrypt 4.3.0 and visible in the test log:
passlib reads `bcrypt.__about__.__version__`, removed in bcrypt 4.1, and logs
`(trapped) error reading bcrypt version` on every run. The library had been degrading for
some time.

### Library choice: direct `bcrypt`, not `pwdlib`

`pwdlib` (the maintained successor, used by fastapi-users, 0.3.1 published 2026-08-12) was
evaluated properly rather than assumed, by running it against the golden hashes:

| Implementation | Verified | Mismatched | **Raised** |
|---|---|---|---|
| `pwdlib` `BcryptHasher`, as-is | 63 / 126 | 0 | **63** |
| direct `bcrypt` + UTF-8 **byte** truncation | **126 / 126** | 0 | 0 |
| direct `bcrypt` + naive **character** truncation | 90 / 126 | 0 | 36 |

`pwdlib`'s `verify` is a bare passthrough — `bcrypt.checkpw(ensure_bytes(password), ...)` —
with no truncation and no option to enable it. It therefore does not solve the problem: the
truncation wrapper still has to be ours, and `pwdlib` would only add a dependency and a layer
of indirection on top of it. Direct `bcrypt` also *removes* a dependency (`passlib`) without
adding one, and `bcrypt` was already a direct, pinned, scanned dependency.

**Path to argon2 is unaffected.** bcrypt and argon2 hashes are self-identifying by prefix
(`$2a$`/`$2b$`/`$2y$` vs `$argon2id$`), so argon2 can be introduced later by dispatching on
that prefix in `verify_password` and rehashing on next successful login — no data migration,
no forced reset. Choosing `pwdlib` today would not have made that step meaningfully cheaper.

## How

### Backward compatibility is the whole job

`CryptContext(schemes=["bcrypt"])` emitted standard `$2b$12$` hashes; `bcrypt.hashpw` +
`bcrypt.gensalt(12)` emits the same format at the same cost. Cost 12 is **pinned explicitly**
rather than inherited from `bcrypt.gensalt()`'s default, so a future bcrypt release cannot
silently move the cost factor for new hashes.

Proving it required hashes made by the code being *replaced*, so they were generated first,
under passlib 1.7.4 + bcrypt 4.3.0, and committed:

- 14 passwords × 9 hash variants = **126 hashes**
- cost factors 4, 8, 10, 12, 13; idents `$2a$`, `$2b$`, `$2y$`
- ASCII, CJK, emoji, accented, whitespace; 71/72/73/100/200-byte lengths

`test_fixture_provenance_is_the_pre_migration_stack` asserts the fixture still declares
passlib 1.7.4 / bcrypt 4.x, so it cannot be quietly regenerated post-migration to make a
failure disappear.

### The 72-byte decision

bcrypt consumes only the first 72 bytes of a secret. passlib truncated silently; bcrypt 5
raises. Three options were considered:

| Option | Verdict |
|---|---|
| SHA-256 pre-hash to remove the limit | **Rejected.** Changes hash derivation; every stored hash becomes unverifiable. Total lockout. |
| Reject >72 bytes everywhere, login included | **Rejected.** Locks out existing users whose password is already over the limit. |
| **Truncate on verify; reject on set** | **Chosen.** Grandfathers every existing hash, stops the population growing. |

Concretely:

- **`app/core/security.py` truncates, on both hash and verify.** Both call one
  `_prepare_secret()`, so their preprocessing can never drift apart — an asymmetry between
  them would be a silent authentication bug.
- **The cut is on UTF-8 bytes, never characters.** `password[:72]` is a different and wrong
  operation: `"密" * 30` is 30 characters but 90 bytes, so character-slicing still hands
  bcrypt 5 an over-length secret. This is exactly the 36 raised cases in the table above.
  Byte-slicing may land mid-codepoint and produce invalid UTF-8 — that is correct and
  intended; bcrypt takes bytes, the result is never decoded, and it is what passlib did.
- **`validate_password_strength` now rejects >72 bytes**, on signup and password-reset only.
  It measures bytes, for the same reason. Login is deliberately untouched.

`SignupRequest.password` / `ResetPasswordRequest.password` had **no** max length, so
over-72-byte passwords were reachable and silently truncated in production data. The check
went into the existing service-layer validator rather than a Pydantic `max_length`, matching
where the codebase already puts password rules, and because Pydantic counts characters.

### One behaviour change beyond compatibility

`verify_password` now returns `False` for a malformed stored hash instead of propagating
`ValueError`. Both passlib and `bcrypt.checkpw` raise on an unparseable hash, which would turn
a single corrupt row into a **500 on the login path**. A hash bcrypt cannot parse can never
authenticate anyone, so `False` is the correct answer; the event is logged (without the hash
or the password) so ops still sees the corruption.

### API contract change (mobile/FE must handle)

New error code on signup and password-reset. It is **additive** — a case that previously
succeeded now fails — so no existing code is renamed:

```json
{"error": {"code": "PASSWORD_TOO_LONG", "message": "That password is too long. Emoji and accented letters take up extra room.", "field_errors": []}}
```

`422`. Note this project's envelope is `{"error": {...}}` with no top-level `success` key.

## Operate / roll back

Nothing to run. **No migration, no data change, no forced password reset** — the stored hash
format is identical before and after.

Rollback is a plain revert of the branch: reverting restores `passlib` + `bcrypt<5`, and
hashes written by the new code (`$2b$12$`) are read back by passlib without issue, so the
change is reversible in both directions. The one thing a revert re-opens is that
`PASSWORD_TOO_LONG` disappears and >72-byte passwords are silently truncated again.

## Follow-ups

- `scripts/gen_passlib_golden_hashes.py` cannot run on the current dependency set (passlib is
  gone). Its docstring documents the throwaway-venv recipe. Regenerating is only ever to widen
  coverage — a failing golden-hash test is a real regression, never a stale fixture.
- Argon2 is now a clean, additive next step (prefix dispatch + rehash-on-login). Not scoped
  here.
- `python-jose` → `PyJWT` remains the open item that clears the accepted ecdsa advisory
  (`PYSEC-2026-1325`, review 2026-11-27) — see the 2026-08-27 SOP. Untouched by this change.
- FE/mobile need to handle `PASSWORD_TOO_LONG` on signup and password-reset.
