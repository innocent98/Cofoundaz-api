# Auth & Onboarding: PRD gap fixes (API)

**What shipped:** the API half of the Module 01 audit (`cofoundaz/docs/checklist/auth-onboarding-prd-gaps.md`, build-order step 1): sign-in lockout per (email, IP) with the same answer for unknown emails, per-route rate limits, a sign-up consent record, an MFA sign-in ticket that survives a typo, an HttpOnly-cookie session mode with a CSRF guard, onboarding input validation, per-row invite results, no draft startup for invited people, a welcome email and in-app notice, and brand-coloured auth emails with the PRD invite subject. FE guide `docs/fe-integration-guide-auth-onboarding.md`. Branch `feature/auth-onboarding-gaps`, PR: see the branch. Migration **`0096_auth_onboarding_gaps`**, chained on `0092_marketplace_providers` for now (0093 to 0095 are in flight in other PRs; the lead re-chains `down_revision`).

**Why:** the audit found a user-enumeration leak in the lockout (a registered email locked, an unknown one never did), a lock anyone could trigger on a victim, no tighter limit than 120/min on sign-up, forgot, resend or login, unvalidated onboarding input (`javascript:` websites, free-text goals, an emailed `"nope"` invite), an MFA ticket that died on the first typo, tokens that the FE kept in `localStorage`, and a consent checkbox the API never recorded. Decisions D-AUTH-1, -2 and -6 (all accepted 2026-11-05) fix the model; this is the build.

**How**

| Gap | Decision |
|---|---|
| 1, 2, 3 Lockout (D-AUTH-2) | The attempt is **reserved atomically** (one `INCR` + `EXPIRE NX` in a MULTI per counter, refused when the count is past the limit, undone on success), so a parallel burst gets exactly the limit, not 60. Counters are Redis keys on **hashes** (`lf:{sha256(email)}:{sha256(ip)}`, `lfe:{sha256(email)}`), never on whether a user row exists, so a real and an unknown address behave identically. Trips at `LOGIN_MAX_FAILS` (5) for a (email, IP); a second counter per email over all IPs trips at `LOGIN_EMAIL_MAX_FAILS` (30) to cap a distributed guess, **but refuses only addresses with no good sign-in to that account in the last 30 days** (a per-account zset of hashed addresses, written on a good login or MFA success, at most 50), so strangers cannot lock the owner out of their own networks. Per-IP counters (here and in the limits below) key on the **IPv6 /64**. The lock lasts `LOGIN_LOCKOUT_MINUTES` from the tripping failure (the key's TTL is reset to the full duration then); attempts while locked are refused **before** the password is checked and are not counted, so they cannot extend it. A suspended account counts as a failure (else it is the one address that never locks). 429 `ACCOUNT_LOCKED` carries `retry_after_seconds` and a `Retry-After` header; the message is the PRD sentence with minutes. A successful reset clears the (email, every IP) keys and the email total (a `SCAN` on a hex-only pattern). The old `users.failed_login_count` / `locked_until` columns are no longer written by login (kept; reset still zeroes them). |
| 4 Rate limits | `app/services/auth/ratelimit.py`: fixed-window Redis counters shared by all workers (slowapi's limiter is per process). Sign-up 10/h/IP, forgot 20/h/IP, resend 20/h/IP, login 60/15 min/IP (all on the IPv6 /64 for v6). Per-IP overruns are `429 RATE_LIMITED`. Per-**email** caps on forgot and resend are **silent**, two of them: 5/h per (email, caller IP bucket), then 20/h per email overall, where the overall counter only counts calls the pair cap let through (one caller adds at most 5/h to it and cannot silence the owner) (generic 200, nothing sent): an error there would reveal whether the address has an account. All tunable by `AUTH_*` env vars. |
| 6 Onboarding input | `app/schemas/onboarding.py`: website http(s) only (a bare domain gets `https://`, credentials and control characters refused), phone 7 to 15 digits, country ISO-2 upper-cased, goals from the eight PRD chips (D-AUTH-7), trimmed text with length caps, blanks rejected (also the BE half of gap 18). Industry stays free text up to 80 characters until Adebayo edits the list. |
| 7 Invites | `results: [{email, status: created\|skipped\|invalid, reason, message}]`, one per row, in order. The email is a plain string so one bad address does not fail the batch; syntax is checked per row with `email_validator` (no DNS). `created`/`skipped`/`undelivered` stay. Shared with `POST /team/invitations`. |
| 8 MFA ticket | Peek the ticket instead of deleting it on resolve; an atomic `INCR` counts each try **before** the code is checked and a try past the cap is refused without looking at the code (a concurrent burst cannot slip past); the 5th wrong code burns it (`MFA_TICKET_EXPIRED`); a correct code **claims** the ticket with `DEL` (exactly one of two concurrent correct submissions wins). Added after the automated security review: a per-**account** cap (`MFA_USER_MAX_FAILS`, 10) across tickets, because someone with the password can mint tickets at will. |
| 11 No draft for invited people | `not_a_founder_state` (GET only): a user with no workspace of their own who is an active member elsewhere, or holds a live pending invitation, gets a member / `pending_invite` state and **no draft is created by reading**. Only an accepted **membership** blocks writing (`409 ONBOARDING_NOT_FOR_INVITED`); a pending invitation is display-only, because anyone can invite any address and a lock would let a stranger stop its owner starting their own startup (Opus review). `POST /invitations/decline` (same checks as accept; new `InvitationStatus.declined`, no migration: the column is a non-native enum) clears it. `UserProfile.role_title` now defaults to `""`; "Founder & CEO" is set when the founder's draft is created. Existing rows are not rewritten. |
| 12 Resend | `{sent, retry_after}`, keyed on the typed address only (same for unknown addresses). |
| 14 Consent | `accepted_terms: true` required (422 `TERMS_NOT_ACCEPTED`); `users.terms_accepted_at` + `users.terms_version` (`TERMS_VERSION` setting) plus the version in the audit row. `SIGNUP_REQUIRE_TERMS` (default true) is a deploy-order escape hatch, see Operate. |
| 21 Welcome | `welcome_email` sent **after commit**, once, by `POST /onboarding/complete` (best effort). The audit found the in-app "Your workspace is ready" never existed: the event `notification.onboarding_complete` was published and nothing listened. One registry row now delivers it to the founder only (category `roadmap_missions`). |
| 22 Emails | Invite subject `{Founder} invited you to join {Startup} on Cofoundaz` (newlines stripped from the subject), button `#0F6AFC`, headline `#051736`; "password changed" notice after a reset or change. The PRD welcome subject has an em dash; the repo's no-dash copy rule (`test_no_em_or_en_dashes_in_api_copy`) wins, so it ships as `Welcome to Cofoundaz: let's build {startup}`. |
| 25 | No change by design: access tokens (15 min) outlive a sign-out. Documented in the FE guide for the security page. |
| D-AUTH-6 Cookie session | Header `X-Auth-Mode: cookie` marks a client that keeps the refresh token only in the HttpOnly cookie: login, MFA challenge, Google exchange and refresh then return `"refresh_token": null`. All four also return `expires_in`. Header-auth clients are untouched (the current FE keeps working until its PR). **CSRF design** (`app/services/auth/csrf.py`): the only cookie-only endpoints are refresh and logout; when the token is not in the body they require `X-Auth-Mode: cookie` (a custom header, so a form cannot send it and a cross-origin `fetch` needs a CORS preflight only allowed origins pass) and, when the browser sent an `Origin`, one of `BACKEND_CORS_ORIGINS`; the cookie stays `SameSite=Lax`, `HttpOnly`, `Secure`, path `/api/v1/auth`. A body token needs none of it (not ambient). 403 `CSRF_REJECTED`. Rejected alternatives: double-submit token (needs a readable cookie or a second endpoint for no gain here), `SameSite=Strict` as default (breaks if FE and API ever sit on different sites; remains an env choice), Origin-only (absent on some non-browser callers, so it cannot be the sole check). |

**Verification:** per-gap unit tests (above), then the full unit suite on a scratch Postgres/Redis (about 5,450 tests; the two failures it showed were a repo rule against dashes in copy and a staff test that expected the old MFA code for a suspended user's ticket, both fixed). Live: `e2e/test_auth_onboarding_gaps.py` (11 journeys) on a real uvicorn, 55 captured bodies feed the FE guide; the existing journeys that touch sign-in, onboarding, settings and invitations were re-run. Local gates: black, isort, ruff, mypy, bandit, pylint (9.85). CI runs the full suite and scans.

How to reproduce the live capture. Two server shapes, each on its own scratch Postgres + Redis (never the shared stack):
1. **CI shape** (`scripts/e2e_run.sh`): `AUTH_*` limits raised to 100000 and `SIGNUP_REQUIRE_TERMS=false`, because 44 journeys sign up in bulk from 127.0.0.1 without the checkbox. The tests marked `strict` skip.
2. **Strict shape**: real defaults except `AUTH_SIGNUP_PER_IP_HOURLY=12 AUTH_FORGOT_PER_IP_HOURLY=6 AUTH_LOGIN_PER_IP_15MIN=20`, with `E2E_AUTH_STRICT=1` exported to the pytest process (and the same three `AUTH_*` values exported to it, it reads them). Run the whole of `e2e/test_auth_onboarding_gaps.py` on it; the limit-exhausting tests are last on purpose. The per-address tests send `X-Forwarded-For`, which uvicorn trusts from 127.0.0.1.

**Opus review fixes (2026-11-05, PR #227):** refresh-token reuse now commits the family revocation before raising (it was rolled back with the failed request, so reuse detection did nothing; test: rollback after reuse leaves zero live sessions); the refresh/logout token source is body-first so a decoy body token next to the cookie cannot dodge the CSRF guard (logout also no longer clears the cookie for an unknown body token); atomic attempt reservation for the sign-in lockout and the MFA per-account cap; known-address exemption and /64 keys; mail caps per (email, IP) + overall; `INCR`+`EXPIRE NX` in one MULTI everywhere (`_incr`, MFA attempts); backup codes spent by one conditional `UPDATE`; bcrypt on unknown / password-less accounts; onboarding invites no longer accept `investor` (`InvitableRole`); decline-invitation endpoint. The review asked for 403 on "cookie plus junk body token": with body-first selection the junk token is simply the (wrong) credential, so refresh answers 401 without touching the cookie and logout is a no-op that leaves the cookie alone, which closes the same hole without breaking the legacy FE, which may send both.

**Operate / roll back**

- **Deploy order (important).** The current FE does not send `accepted_terms`, and its onboarding goals are free text. Until the FE PR is live, either deploy the FE first, or set `SIGNUP_REQUIRE_TERMS=false` on the API (goals cannot be relaxed: the old chips will 422). New e2e journeys that sign up without the checkbox are fine on the CI server (consent off); **staging's live-e2e gate signs up without it** (only `make_verified_user` sends it) and from one runner IP, so on staging set `SIGNUP_REQUIRE_TERMS=false` and raise the `AUTH_*` limits for the gate, or it will hit 422 / 429.
- **Proxy IP.** Per-IP limits and the lockout trust `request.client.host`. nginx overwrites `X-Forwarded-For` with `$remote_addr` and gunicorn's uvicorn worker is told to trust it through the `FORWARDED_ALLOW_IPS` env var (`deploy/nginx/snippets/proxy-backend.conf`, `docs/deployment/NGINX_TLS.md`), so this should be the real client. **Not verified on staging.** Check by signing in wrongly 5 times from two different networks: only the first should lock. If every client shares the proxy's address, set `FORWARDED_ALLOW_IPS` correctly before launch or one user's failures will lock everyone.
- **Redis is now in the sign-in path.** Login, sign-up, forgot, resend and the MFA challenge need Redis (forgot and resend already did). If Redis is down they answer 500, not "open".
- **Hash keys:** `kip:*` (known addresses), `rl:*` (limits), `lf:*`/`lfe:*` (lockout), `mfa_fail:*`.
- **Unlock someone by hand:** `redis-cli --scan --pattern 'lf*'` finds the keys but they are hashed; the supported way is the password reset (which clears them). To clear everything: `redis-cli --scan --pattern 'lf:*' | xargs redis-cli del` (and `lfe:*`, `mfa_fail:*`).
- **Roll back:** revert the PR; downgrade `0096` drops `terms_accepted_at` and `terms_version` (consent records are lost). `role_title` defaults and Redis counters need no cleanup (counters expire within the hour).
- Env: `AUTH_LOGIN_PER_IP_15MIN`, `AUTH_SIGNUP_PER_IP_HOURLY`, `AUTH_FORGOT_PER_IP_HOURLY`, `AUTH_FORGOT_PER_EMAIL_IP_HOURLY` (5), `AUTH_FORGOT_PER_EMAIL_HOURLY` (20), `AUTH_RESEND_PER_IP_HOURLY`, `AUTH_RESEND_PER_EMAIL_IP_HOURLY` (5), `AUTH_RESEND_PER_EMAIL_HOURLY` (20), `LOGIN_EMAIL_MAX_FAILS`, `MFA_TICKET_MAX_ATTEMPTS`, `MFA_USER_MAX_FAILS`, `TERMS_VERSION`, `SIGNUP_REQUIRE_TERMS`. None is a secret.
