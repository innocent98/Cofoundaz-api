# SOP — Finance final re-check fixes: D9 (AI reply never ends) and D10 (bank rows editable)

**What shipped.** Branch `fix/finance-d9-d10`, no migration. Two API defects from the final Finance re-check (FE PR #163 rows D9, D10). PR: see the PR for this branch. FE guide updates: `docs/fe-integration-guide-ai-cofounder-chat.md` (§5) and `docs/fe-integration-guide-finance-payments.md` (§4).

## Why
* **D9.** The Advisor question "What levers should I look at first?" made the real model return an empty completion. The worker logged `LLM API returned an empty completion.` on each of 5 attempts and the assistant message stayed `generating`, so the drawer showed "Thinking..." forever.
* **D10.** A `source: bank` (Mono) ledger row accepted `PATCH {"amount_minor": ...}` and `DELETE` with 200. Only Paystack and Flutterwave rows were protected (`_PROVIDER_SOURCES`).

## Root cause (D9, from the code; the real model was not called)
`LLM_MODEL=gpt-5.6-luna` is a reasoning model and the client sends `max_completion_tokens`, which **counts hidden reasoning tokens**. Chat replies were capped at `LLM_MAX_TOKENS=800`. An open "which levers first" question, now with the slice (e) finance paragraph in the system prompt, makes the model reason about many options; when the reasoning alone uses the 800 tokens the API answers `finish_reason: "length"` with `content: ""`. That is exactly the "empty completion" log, it is prompt-shaped (neighbouring wordings reason less), and it is deterministic, so every retry hit it. Nothing logged `finish_reason`, which is why it looked like a mystery.

## How
| Item | Decision | Rejected |
|---|---|---|
| Cause (b) | Chat turns use a new `LLM_CHAT_MAX_TOKENS` (default 3000) instead of 800. `OpenAILLMClient.complete` also retries **once** with 4x the budget (ceiling 16000) when the completion is empty **and** `finish_reason == "length"`; both calls' tokens are metered. Every empty completion logs `finish_reason`, `reasoning_tokens` and the budget at WARNING, and the error text carries them. | Sending `reasoning_effort` (an unverified parameter for this model; a 400 would break every call). Changing the question wording (FE already avoided it; the cause is the budget). |
| Cost bound | An empty completion that survives the larger retry (or is not `length`, e.g. a content filter) raises `EmptyCompletionError`; the chat handler ends the turn `failed` at once instead of retrying the job, so a stuck prompt costs at most one attempt (about 15k tokens), not 5. The client also skips the larger retry when `llm_budget.headroom` (daily budget left) cannot cover it. Tokens of failed calls are billed on their own session (`_debit_independent`), because the job savepoint rolls back the caller's writes. | Leaving retries to the worker (up to 75k tokens on one bad prompt). |
| `content: null` | `_content` now maps a null `content` (refusal, content filter, spent budget) to `""`. It used `str(None)`, which would have shown the founder the word "None" as the answer. | — |
| Ending a turn (a) | `handle_cofounder_reply` re-raises provider errors while `job.attempts < WORKER_MAX_ATTEMPTS` (normal backoff retries). On the last attempt it logs, marks the message `failed` with founder-visible text (`REPLY_FAILED_TEXT`) and returns, so the job ends `succeeded` (the turn is settled; nothing left to retry). Over budget keeps `failed` but now carries `BUDGET_FAILED_TEXT` instead of empty content. | Re-raising on the last attempt (the savepoint rolls the `failed` write back). |
| Event | `fail_message` publishes `ai.cofounder.reply.failed` on the event bus. The FE has no stream for chat: it polls `GET /ai/conversations/{id}` and sees `status: "failed"`. | Inventing an SSE channel. |
| Stale | `fail_stale_generating` fails assistant turns `generating` longer than `AI_REPLY_STALE_SECONDS` (default 900, just past the last retry at about 7.5 minutes). It runs on `GET /ai/conversations/{id}` (commits when it changed anything) and on `POST .../messages` before the 409 in-flight guard, so a dead worker can no longer lock a conversation. | A scheduler job (reads and the next send already cover every visible case). |
| D10 | `_IMPORTED_SOURCES` = bank, accounting, paystack, flutterwave. For these, PATCH is category-only and DELETE is refused with the existing 422 (`field: source`, "Imported transactions are read-only except the category."). Invoice and expense rows keep their own messages; `manual` stays fully editable. | A per-source message (the FE and guide already rely on one shape). |
| Bank row deletion paths | Checked: Mono/Paystack **disconnect keeps history** (`connections.disconnect` only wipes secrets, covered by `test_disconnect_wipes_secrets_keeps_rows`), and nothing else deletes bank rows. Expense and invoice services delete only their own `expense`/`invoice` rows via `db.delete` in the service, which this change does not touch. | — |

## What's involved
`app/platform/llm.py` (empty handling, `finish_reason` log, `EMPTY_RETRY_*`), `app/core/config.py` (`LLM_CHAT_MAX_TOKENS`, `AI_REPLY_STALE_SECONDS`), `.env.example`, `app/worker/handlers/ai.py` (`handle_cofounder_reply`), `app/services/ai_cofounder/service.py` (`fail_message`, `fail_stale_generating`), `app/api/v1/endpoints/ai.py`, `app/services/finance/service.py` (`_IMPORTED_SOURCES`).

## Verification
* Unit: `tests/platform/test_llm.py` (length-empty retry with a larger budget and double metering, still-empty raises with `finish_reason`/`reasoning_tokens`, `content_filter` not retried, `null` content), `tests/worker/test_cofounder_reply_handler.py` (empty-completion stub through `runner.run_once`: attempts 1 and 2 stay `generating` and requeue, attempt 3 ends `failed`, event published; stale sweep), `tests/api/test_ai_chat.py` (stale read then re-send allowed), `tests/api/test_finance_sync.py::test_every_imported_source_is_category_only` (bank, accounting, paystack, flutterwave: amount, direction, mixed body and DELETE all 422; category 200).
* Live: `e2e/test_finance_d9_d10.py` against real uvicorn: Mono and Paystack rows refused with the shared 422, category 200, manual row edit and delete 200; a reply whose LLM keeps failing ends `failed` after 5 worker runs; an aged `generating` reply is failed on read. Captures in `e2e/_captures/finance_d9_d10/`.
* **Not verified here (the lead verifies live):** that the real model now answers "What levers should I look at first?" with the 3000 cap. The cause is inferred from the API contract and the code, not from a captured `finish_reason`; the new WARNING line prints it if the cause was something else.

## Operate / roll back
No migration, no new required env var. Optional: `LLM_CHAT_MAX_TOKENS`, `AI_REPLY_STALE_SECONDS`. Revert the PR to roll back. Token cost: chat turns can now spend up to 3000 (6 times the old cap) completion tokens against the per-startup daily budget.

## Follow-ups
* If the live check still shows an empty reply, read the worker log's `finish_reason`/`reasoning_tokens` line and raise `LLM_CHAT_MAX_TOKENS` or add a reasoning-effort setting once the parameter is confirmed for the model.
* Other `ai.*` handlers use `LLM_MAX_TOKENS=800` too and could hit the same reasoning-budget issue; the client-level one-shot retry now covers `complete()` for all of them (not `complete_json`).
